## 开场（约 1 分钟）

大家好。我是熊镇正，来自香港中文大学（深圳）。

今天讲的是我一个人做的一套东西 —— **Soundtrace · 明略播客个性化后期剪辑助手**。

一句话定位：**这不是"一键出片"的黑盒。它是一套本地跑、每一步都能监控、由真人签字的多轨播客后期助手。它不追求点一下就出成品，它追求把重复劳动取代掉、把人的剪辑偏好学下来、把每一次决定都变成下一期节目能用的经验。**

我今天分五段讲：先放一段 A/B demo；然后讲背景 —— 播客后期为什么难；接着从**流程图**切入技术思路；再从 **skill** 切入工程框架；最后聊一下下一步。

## 一 · Demo · A/B 录频（约 3 分钟）

现在放两组音频进行比较。

- **A 版** · 原始 3 轨对齐录音，没做过任何处理。
- **B 版** · 系统提议、我批准之后的机器辅助版。我们内部管这个叫 `machine_assisted_draft` —— 机器提议、人签字。

请大家的耳朵抓这三个地方：

**第一 · "呃"剪没剪干净。** 边界不是靠 ASR 给的粗时间戳，是靠 **MFA 音素级对齐**算出来的。粗时间戳会把下一个词的辅音起音吃掉；音素级不会。

**第二 · "第一、第二、第三"这类层级词剪掉之后的节奏。** 不是把词剪掉就完了 —— 原位置会留 **300 到 500 毫秒的空白**，模拟真人思考的停顿，不是硬贴上去。

**第三 · 改口** —— "怎么保证 → 怎么确保"。这类要么整对保留、要么整对剪掉，**不允许剪一半留一个**，那样语义会断裂。这个约束叫 `self_correction · 全或无`，是 08-17 mentor 听审当天定的死规矩。

一句话总结这个 demo：

> **剪不止是要剪掉东西。剪完之后还要考虑这一处于什么位置、要不要补一个停顿、去模拟真人节奏。这是这个项目的核心命题。**

## 二 · 背景 · 为什么这件事难（约 3 分钟）

先讲播客本身。单期 30 到 60 分钟深度对话，3 轨对齐录音。

大家可能觉得后期不就是 "把'呃'剪掉" 吗？不是。真正的难点是四条。

### 第一条 · 每一刀都要 crossfade

播客后期不是一次性拉一根曲线就完事。每一处删除都是一刀；每一刀在波形上都是一个断口。断口直接对拼 —— 专业词叫 **butt splice** —— 十有八九能听出 "咔" 一下。所以专业剪辑师每一刀都要做一次淡入淡出，用几十毫秒的曲线把断口糊过去，这个叫 **crossfade**。

一集 60 分钟深度对话大概有几十甚至上百个"呃 / 嗯 / 重复 / 改口"候选点。而且 crossfade 长度不能拍脑袋 —— 如果紧挨着的下一个词是**辅音开头**，比如 "确" 这种 q- 起音，crossfade 太长会把辅音吃掉，那个词变成 "ue 保"；太短又糊不干净。我们默认 crossfade **30 ms**，`cut_parameters.json` 里按语义类别 override —— 长停顿 200 ms、说错重来 60 ms 之类。

### 第二条 · 多轨对齐 · 不能差一个 sample

输入是 3 条**同步录音**。所有剪辑决策必须**整数 sample 一致**地作用到 3 条轨道上 —— 差一个 sample 就有相位问题，声音变得像水下面听一样闷掉。

这一条我们做到了代码强制：`render_approved_edl.py` 里 EDL 的 `time_base_hz` 必须等于 sample_rate，`start_sample` 全部 int，不吃 sub-sample 偏移。这也是元规则 **M4 · EDL 整数 sample** 写进项目宪法的原因。

### 第三条 · 公司音频不能上云

未发布的对话内容属于合规敏感数据。所有云端 SaaS —— Descript、Adobe Podcast —— **一概不能用**。必须本地闭环，拔掉网线也能跑完。

这带来一个非常具体的约束：LLM 判决层要么用本地小模型（品味不够），要么用 `claude CLI` 这种 subprocess 调用（走用户 shell、无 API key、原文不外传）。后面讲 Stage 3.7 会展开。

### 第四条 · 语义判断只有耳朵能做 —— 08-19 这一条被改写了

**08-19 号之前项目的整条命题一直是**："这句话是废话还是伏笔？这个停顿是尴尬还是节奏？这是耳朵和品味的事，AI 现在还做不了。所以规则给答案 · 人推翻错案。"

**08-19 号晚上，这一条被改写了**：人还是最终签字方，但**候选的语义判决权已经交给 LLM**。以前是"20 层规则堆着判 · 越堆越弱智"，现在是"**LLM 唯一判决 · 规则退到召回和物理约束**"。

后面 Stage 3.7 那段是这次 pre 的重头戏，我会展开讲。

### 3.1 端到端流程图

从原始 3 轨 WAV 到发布级 mp3，整条 pipeline 一条命令跑完，主 orchestrator 就一个文件 —— `稳定生产/challengers/e2e-auto-runner-v1/scripts/run_end_to_end.py`（2103 行，含所有 stage）：

      ↓（若 3.5.5 skip，才走 3.7 的 fallback）
Stage 3.6 · autocut_gate · 只留 4 结构性门
             speaker_role · source_track · G6_duration · review_budget
             语义门 G3 / G5 / G7-session / G7-protection 让位 diagnostic_only
      ↓
Stage 3.7 · LLM 语义 filter · 唯一"该不该剪"判决（fallback / 补漏）

      ↓

      ↓
Stage 6.7 · Optuna TPE 参数级迭代（这里跟 LLM 完全分离 · 见下）

      ↓

### 3.2 LLM 与 Optuna 的分工 · 这是全项目最容易混淆的一点

**要把这两个组件的职责讲得干净。它们完全分离 · 不联动 · 不共享判决权。**

| 组件 | 归属 | 干什么 | 输入 | 输出 |
|---|---|---|---|---|
| **LLM · Stage 3.5.5 / 3.7** | 语义层 | **该不该剪** —— 剪不剪、这一处是不是废话 | transcript context ± 5 s · 剪的词 · kind | `verdict ∈ {KEEP_CUT, REJECT_KEEP, NEEDS_REVIEW}` · reason · confidence |
| **Optuna · Stage 6.7** | 参数层 | **怎么剪** —— crossfade / pause / boundary offset 具体是几毫秒 | 已经在 `verified_edl.json` 里、且 `verdict != REJECT` 的候选 | 每候选的 `final_params` |

**Stage 6.7 Optuna 探索的候选池 ≠ EDL**。EDL 里只有 LLM KEEP_CUT，但 Optuna 会连**非 REJECT 的所有候选**都跑一遍（包括 REJECT_KEEP 和 NEEDS_REVIEW）。原因是"全走 Optuna" —— 08-19 号我明确的：**关 Stage 4.5 的 NISQA gate**（Check 5），改成让 Optuna 自己探参数、把这些候选的 `refinement_trace` 侧写到磁盘，作为**未来学习的历史 trace**。它们不会因此进成品，因为 EDL 早在 Stage 5 就只装 KEEP_CUT。

**那 Stage 6.10 那个 "LLM ∩ Optuna 交集" 是什么** —— 是最后一道 **apply 门**。Optuna 是纯数值优化器，它给一个 REJECT_KEEP 的候选也可能找到"参数上收敛"的组合。这不代表这个候选应该被剪。所以 6.10 加一道 gate：**只把参数真正写回成品到既 KEEP_CUT 又 converged 的候选**。语义判决权最后一次还给 LLM。

**EP05 这次演示了这个门生效**：
- LLM KEEP_CUT = `{C004}`
- Optuna converged = `{FAM-self_correction-...}`
- 交集 = **空** → **skip re-render** · 成品用 default automix

如果没有这道门 · Optuna 就把好参数应用到 FAM-self_correction · 但 LLM 已经判它 REJECT_KEEP · 结果是**剪掉了一个不该剪的地方**。这道门看起来啰嗦、但它是防呆的核心。

一句话总结：**LLM 管 candidate · Optuna 管参数 · 两者不联动 · 交集只是防呆**。

### 3.3 08-19 evening 的架构级冻结 · 让位与保留

**冻结前 · 08-19 白天** ——
- autocut_gate 7 门（4 结构 + 3 语义 G3 / G5 / G7）
- 剪不剪由 gate + cut-verify verdict 判决
- LLM 只是 sidecar · 提议 · 不决定 EDL

**冻结后 · 08-19 evening** ——
- autocut_gate 只留 **4 结构性门**：speaker_role / source_track / G6_duration / review_budget
  - 4 门管**物理约束**：剪错人不行、伪影不行、超过 0.8 秒的段剪不干净、人审预算有限
  - 语义门 G3 / G5 / G7 全部让位 —— 保留代码，verdict 打上 `"diagnostic_only · LLM 已接管"`，只做诊断，不决定 EDL
- **Stage 3.5.5 / 3.7 LLM 唯一决定 "该不该剪"**
  - Claude subagent · 3 mode 优先级：
    - Mode 1 · `claude CLI` subprocess 首选 · 无 API key · 无 SDK · 走用户 shell · **EP05 实际走的就是这条**
    - Mode 2 · Anthropic API SDK
    - Mode 3 · 半自动 fallback · 只写 `candidates_with_context.json`
  - Prompt 给它 5 秒前文 + 剪的词 + 5 秒后文 + 候选 kind
  - 输出 `verdict ∈ {KEEP_CUT, REJECT_KEEP, NEEDS_REVIEW}` + `reason` + `confidence ∈ {high, medium, low}`
  - 中文特殊判决原则：`就是` / `这个` / `那个` 语境敏感 · 句号后新句 REJECT · 跨说话人 REJECT · 长停顿话轮转换 REJECT
- **Stage 5 EDL 只读 LLM KEEP_CUT**：`stage_edl_from_gate` 里 `llm_keep_cut_ids = {v.candidate_id for v in llm_verdicts if v.verdict == "KEEP_CUT"}`，其它一律丢
- **Stage 3.5.5 的 discover 分支**：LLM 从 transcript 直接扫出的 KEEP_CUT 如果不在 rules 的 auto_cut 里，也可以直接构 render_sync_cut · 走 EDL —— 意思是 LLM **不只是过滤 rules 候选，还能自己新增**

**冻结证据 · EP05-GOLDEN-PATH-20260819-1900**：
- 老 rules pipeline · 36 候选（其中 33 是 cough_like 误报）· 33 cuts
- 新 LLM-first · 2 候选 → LLM 判 **1 KEEP + 1 REJECT · 全 high confidence** → EDL 1 cut · NISQA overall = 2.854 · discontinuity = 4.114
- 与我本人直觉 100% 一致

浓缩一句话：

> **5 门语义规则让位 · 4 门结构性门保留 · LLM 唯一决定候选 · Optuna + NISQA 只做参数与打分。规则不死 · 让位而已。**

### 3.5 核心思路四条

1. **机器只提议 · 人签字**。机器输出叫 `machine_proposed_*`，人批准后才升级 `human_approved`。不允许自批准、超时批准、把机器预测伪装成人审。
2. **规则通过配置迭代 · 不改代码**。每条规则一个 JSON（`candidate_rules.v18.json` / `refinement-policy-v1.json` / `session_feedback.jsonl`）。改规则改配置。
3. **A/B 试听是唯一验收方式**。任何"这一版是不是变好了"必须落到 A/B clip 上 —— 用耳朵听、不看数字。A/B clip 强制先跑 automix + loudnorm，避免响度差异误判。
4. **每期节目独立 run 目录 · 可回滚**。`main/runs/EP05-GOLDEN-PATH-<时间戳>/`，`run_identity.json` 冻结 8 项 SHA（preference / candidate_rules / editing_policy / integration_registry / music_asset / music_template / experience_snapshot / audio）· 回滚就是删目录的事。

### 4.2 Skill 底下是 Tool · 契约先行

每个 skill 管一组 tool。当前登记在册 **58 个 tool**，全部写在 `main/tools/tools.json`。每个 tool 声明：

- 唯一名字
- 输入 / 输出 / 超时
- 依赖脚本的 SHA（脚本被改了 SHA 变了、下次调用报错）
- v2 adapter（当前 **52 项标 adapter_registered · 2 项 promoted · 1 项 skeleton · 3 项未覆盖**：`run_versioning_guard` / `generate_ab_clip_learning_driven` / `load_session_feedback` —— Session 2 补齐、Session 3 顶替 v1）

好处 4 条：
1. **加新能力不改主流程** —— 08-19 一次晋升 4 个 Challenger，只加了几个 stage 调用块，主流程结构没动
2. **SHA drift 检测** —— experience snapshot / case memory / voice entrance / music asset / candidate_source · orchestrator 全 fail-closed
3. **写盘权限强制** —— tool 声明目录，非本目录写盘拒绝
4. **未登记即报错** —— `verify.sh` **Layer 21** 静态扫 `main/orchestrator/*.py`，白名单外未登记直接 FAIL

### 4.3 三态代码 · Champion / Challenger / run-local

- **Champion** · 稳定生产线代码，**只读**（这条是**文档纪律 + M1**，不是 os 层强制 —— 没 chmod、没 git hook。靠人和 verify.sh 抽查）。改要走 "冻结 benchmark + 独立复核 + 回滚方案 + 人工签字" 四道门。
- **Challenger** · 隔离实验区，`稳定生产/challengers/<name>/`。**目前 29 个 Challenger**。新能力先在这里做。
- **run-local** · 每期节目的工作区，`main/runs/<run-id>/`。所有产物、日志、SHA 都在。回滚就是删目录的事。

为什么这么分：因为要**同时**满足 —— 实验可以激进 · 生产必须保守 · 每期节目可回滚。这三条同时成立只能靠物理隔离，不能靠自觉。

### 4.4 六条元规则 · 项目宪法 · 老实说说哪些是代码强制、哪些是纪律

顶层还有 6 条元规则，写在 `CLAUDE.md` 顶部 82 行，agent 一分钟读完。任何一条不成立、这个项目就不存在。**但说实话，六条里只有一半是代码硬强制、另一半是纪律**——我把哪些是哪些讲清楚，比吹"代码不允许"要诚实：

| 元规则 | 强度 | 强在哪 |
|---|---|---|
| **M1 · 分层** | 文档 + Layer 13 抽查 | Champion 目录只读**没有 chmod / git hook** · 靠 verify Layer 13 扫 skill status |
| **M2 · 只读** | SHA pin | DeepFilterNet CLI SHA pin · ffmpeg SHA pin · **未在 os 层强制**，主要靠自律 |
| **M3 · 人签字** | 部分强制 | `experience_snapshot / candidate_source / human_decisions` SHA drift fail-closed · `machine_assisted_draft` vs `human_approved` 命名硬区分 |
| **M4 · EDL 整数 sample** | **硬强制** | `render_approved_edl.py` `time_base_hz != sample_rate` raise · `start_sample` int 强制 |
| **M5 · 契约先行** | **硬强制** | verify.sh Layer 12 · Layer 21 · executor_v2 `unknown adapter` 拒跑 · adapter dry_run `wraps_script not found` 拒 plan |
| **M6 · 报告纪律** | 文档 | 三档措辞规范 · **无代码断言** · 靠 review |

意思是：**M4 M5 是真硬强制** —— 这两条违反了 pipeline 起不来。**M3 部分强** —— SHA drift 会 fail-closed。**M1 M2 M6 主要是纪律** —— verify.sh 抽查、剩下靠人守。

我把这个诚实交代出来，因为如果讲成"代码不允许违反元规则"就是吹大了；老实说"哪些是钢丝网 · 哪些是行为规范"反而更能让人信这套系统。

**元规则之下**还有 22 条**域规则**（`docs/domain-rules.md`），规定 "什么时候用什么工具、什么参数、什么门槛"。其中 **cut-verify 域拥有最高优先级** —— 一切规则遇到冲突向 cut-verify 让步。因为 "剪得干不干净" 是最终交付质量，其他规则可以妥协、这一条不能。

### 4.5 4 个 Challenger 晋升 · 独立复核 DEFERRED 这一条我要专门讲

08-19 号 4 个 Challenger 一起晋升到 Champion pipeline（NISQA cutverify + benchmark · pyannote diarization · Optuna iterative-cut-refinement · case-memory-embedding）· 全 default ON。按 M1 严格讲 · Champion 只读 · 晋升要走四道门：

| 门槛 | 这次怎么做 |

这就是这个项目最想让人看到的东西。

### 4.6 让位的规则 · 代码保留 · 不删

08-19 让位的东西**代码全部保留**，只是 verdict 降级为 diagnostic。为什么不删：万一 LLM 挂了、或哪天想 rollback，opt-out flag 一开这些规则立刻回归 verdict。

| 让位组件 | 原角色 | 现角色 |
|---|---|---|
| G3 · no_preserve | 保护片头 5 s / 片尾 10 s | LLM 判 · verdict = `"diagnostic_only · LLM 已接管"` |
| G5 · case history | 历史 accept 率 ≥ 阈值自动通过 | LLM 判 · 案例改喂 embedding + few-shot prompt |
| G7 · session_feedback | 用户反馈规则 verdict | LLM 判 · 但 `never_cut` hard override 保留（M3 兜底） |
| G7 · protection | opening / closing 保护 | LLM 判 |
| cut-verify Check 1-4 verdict | 决定 EDL | 只写 `recommended_params`，供 Stage 6.7 Optuna 参考 |
| cut-verify Check 5 · NISQA gate | 剪不干净就 reject | **关** · 只跑 benchmark |

一句话：**规则从"判官"降为"顾问"。判官这个岗位交给 LLM · never_cut 是 mentor 保底红牌**。

## 五 · 下一步 · 从"技术攻关"进入"偏好积累"（约 1 分钟）

MFA 音素级对齐、autocut 4 结构性门、Stage 3.5.5 / 3.7 LLM 唯一判决、Stage 6.7 Optuna TPE、Stage 6.5 NISQA benchmark、Stage 6.8 case embedding sidecar 全部落地之后 —— **基础技术层基本收敛了**。后面迭代重心从 "技术攻关" 进入 "**偏好积累**"。四个方向：

2. **warm-start 从硬编码升级为读文件**。老实说 · Stage 6.7 现在的 warm-start per-kind 起点**还是硬编码在 `optuna_refine.py` 里** · YouTube 42 条已 supersede、mentor gold `cut_parameters.json` 也还没接进去。下一步就是把两个学习来源真消费掉，让 warm-start 变活。
3. **双语 · 多语支持**。MFA 已接 `english_mfa`，`--language auto` 中英自动分派；pyannote community-1 对多语说话人也 OK。海外嘉宾、中英混说场景零成本接入。再加一种语言就是加一个 dictionary 的事。
4. **场景外扩**。同一套框架 —— 机器提议 + 人签字 + A/B 验收 + 本地可追溯 + 契约先行 —— 几乎可以原样搬到相邻场景：访谈类粗剪、会议纪要、口述历史、多语言配音后期、企业内部合规删减。核心机制都一样。
