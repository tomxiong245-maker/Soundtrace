# 开发与文档规则

> 目标：让文档服务于决策和验收，而不是继续积累只适合 AI 阅读的会话流水账。

## 1. 唯一信息层级

| 层级 | 文件位置 | 回答什么 | 更新时机 |
| --- | --- | --- | --- |
| 人类入口 | `README.md` | 这是什么、做到哪、下一步是什么 | 总体状态发生明显变化 |
| 长期记忆 | `统筹全局/全局统筹记忆.md` | 产品、架构、边界和长期方向 | 新产品/架构决定 |
| 当前状态 | `统筹全局/当前项目进度.md` | 已完成、未完成和当前完成门 | 任务或验证状态变化 |
| 产品要求 | `统筹全局/产品要求与验收标准.md` | 什么才算 MVP 完成 | 需求或验收口径变化 |
| 功能说明 | `统筹全局/功能说明/Fxx-*.md` | 一个功能的输入、输出、现状和验收 | 该功能状态或契约变化 |
| 工程证据 | 功能目录、Challenger、`main/runs/` | 命令、日志、哈希、测试与原始报告 | 每次实际执行 |
| AI 交接 | `与AI的上下文/当前项目上下文.md` | 跨对话整体状态和阅读路由 | 当前任务或总状态变化 |
| 历史 | `归档/` | 为什么曾经这样做 | 不再作为当前事实来源 |

同一事实只在一个权威位置完整描述；其他文件只摘要并链接，不复制大段内容。

## 2. 默认阅读顺序

任何 AI 或工程执行者开工前只需要：

1. `统筹全局/全局统筹记忆.md`
2. `统筹全局/当前项目进度.md`
3. 与本任务对应的一份功能说明
4. 本轮任务书和直接证据

归档、旧会话压缩和无关功能文档默认不读。若需要追查历史争议，再按链接进入归档。

## 3. 功能文档的粒度

不采用“每个脚本一个 MD”，否则会再次文档爆炸。采用“每个可独立验收的能力一个 MD”。

一份功能文档必须固定包含：

```text
功能目的
在总流程中的位置
输入与输出契约
已验证事实
已决定方向
待验证假设
不负责什么
验收标准
实现与证据入口
```

脚本新增、重构或参数变化通常只更新对应功能文档的“实现入口”和“当前状态”，详细日志仍放 run/Challenger。

## 4. 不再生成逐会话长摘要

`与AI的上下文/` 顶层只保留：

- `README.md`
- `当前项目上下文.md`

一次对话结束后：

- 新产品/架构决定 → 更新《全局统筹记忆》；
- 当前状态变化 → 更新《当前项目进度》；
- 功能变化 → 更新对应 Fxx 文档；
- 命令、测试、SHA、失败 → 写入对应 run 或 Challenger；
- 纯对话过程不落盘；确有保留价值的原始会议/决策材料进入归档。

不要再创建 `YYYY-MM-DD-音频剪辑上下文压缩.md` 一类不断追加的总文件。

## 5. 三档证据规则

- **已验证事实**：实际运行、检查或人工确认，并有证据路径。
- **已决定的方向**：团队已选择但尚未完成验证。
- **待验证假设**：合理但未证明。

以下词不能混用：

| 证据 | 可以说 | 不可以说 |
| --- | --- | --- |
| 文件/代码存在 | 已落盘、静态准备 | 已运行、已通过 |
| 自动测试通过 | 规则或代码在 fixture 中通过 | 真实内容安全、用户认可 |
| 真实音频跑过 | 该输入可运行 | 可泛化、可发布 |
| bulk accept | 链路 smoke test | 真人逐项精审、训练标签 |
| 真人短片审核 | 短片验收 | 整片可发布 |
| 整片发布验收 | 当前一期可作为发布候选 | 已证明跨节目泛化 |

## 6. 代码与目录边界

- `main/`：编排、状态、工具注册、知识快照引用和每期运行记录，不藏剪辑规则。
- `稳定生产/scripts/`：单一确定性动作，不藏多阶段编排。
- `稳定生产/rules/`：版本化规则与参数；旧版保留可回滚。
- `稳定生产/challengers/`：新工具、新规则和新模型的隔离实验。
- `端到端学习剪辑/`：历史实验和旧实现，不继续堆新生产代码。
- `main/runs/<EP>/`：每期计划、状态、决定、manifest 和反馈包。
- 原始素材、Mentor 成果、Champion 和已哈希历史 run 只读。

## 7. 外部依赖规则

接入仓库、Skill、模型或前端包前记录：官方 URL、版本/commit、下载时间、SHA、代码与权重许可证、依赖、遥测、网络、动态代码、数据流、本机内存/速度和卸载路径。

禁止 `curl | sh`、不透明 `inference.sh`、全局覆盖系统 Python、未经审计上传真实素材。依赖放在 Challenger 独立环境。

## 8. 人工审核规则

- 语义删剪必须真人批准。
- Agent 不得自批准、超时批准、默认全接受。
- `WAITING_FOR_HUMAN_REVIEW` 是正常状态。
- 每项决定必须可回到 reviewer、时间、试听、边界、候选、规则和源文件版本。
- bulk accept 只能作为流程测试，不能计入训练数据或正式精审。

## 9. 修改前后检查

开工前：

1. `git status --short`，不要清理他人改动；
2. 读取权威文档和本功能说明；
3. 复现基线、记录 SHA；
4. 对不上则停止，不改 benchmark 迎合实现。

交付前：

1. 区分静态、测试、真实运行、真人和发布证据；
2. 列出实际修改、实际命令、失败和未完成；
3. 更新《当前项目进度》和对应功能说明；
4. 验证所有链接和路径存在；
5. 不自行晋升 Champion。
