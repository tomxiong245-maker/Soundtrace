# 版本同步与交付事实门

> 契约：`delivery-sync-v1`（2026-08-14）
> 目的：防止“代码、审核页、run 产物、说明文档”各自前进，最后出现 ASR、版本或审核能力不一致。

## 唯一事实来源

以后不要用聊天记录里的“最新”“上一版”判断项目状态。按下面的优先级读取：

1. **音频和审核事实**：当前 run 的 `run_identity.json`、`state.json`、各 manifest 和 SHA。
2. **当前项目状态**：`统筹全局/当前项目进度.md` 中的 `CURRENT_DELIVERY_FACTS` 结构化块。
3. **长期决定**：`统筹全局/全局统筹记忆.md`。
4. **功能契约**：对应 Fxx 文档与《Agent交付流程-从音频到成片.md》。

如果这四层互相矛盾，状态只能写成 `BLOCKED / NEEDS_SYNC`，不能挑一个看起来更新的文件继续跑。

## 每次变更必须走的同步顺序

### A. 先声明变更范围

在开始改动前写清楚它属于哪一类：

- **上游音频变更**：原始 WAV、降噪参数或降噪产物 SHA 变了；必须重新检查 ASR 复用资格，不能沿用旧 transcript。
- **分析变更**：ASR 引擎、模型、解码参数或 semantic 源变了；必须新建分析证据并更新复用清单。
- **候选变更**：规则、偏好或风险门变了；冻结新的候选/审核包，但可以复用 SHA 一致的 `faster-whisper small` 结果。
- **审核产品变更**：前端、审核字段、校验或保存接口变了；不重跑音频，使用 `delivery_orchestrator.py refresh-review`，先归档旧审核包，再重建新包。
- **交付变更**：EDL、渲染、音乐、响度或最终决定变了；必须更新 run 内 manifest、QC 和交付报告。

### B. 变更后的固定动作

每一类变更都必须按这个顺序留下证据：

```text
改代码/规则
→ 跑契约测试
→ 在同一 run 或明确的新 run 实跑
→ 校验 run identity / 输入 / 产物 SHA
→ 更新 CURRENT_DELIVERY_FACTS
→ 更新当前项目进度.md、全局统筹记忆.md 和涉及的 Fxx/操作文档
→ 运行 main/orchestrator/check_current_delivery_sync.py --check
→ 才能对外说“当前版本”
```

没有最后一道同步检查，不能把某个页面、某个音频或某份报告称为最新结果。

## 上下文压缩与 Agent 交接检查点

聊天上下文不是项目事实来源。自动压缩可能在 Agent 无法提前收到事件通知时发生，因此不能把“压缩前我会记住”当作保障。正确做法是：**用户一旦确认硬要求，就立即落盘，不等到压缩发生。**

以下时点必须先写检查点，再继续：

- 收到新的明确偏好、否决或验收要求；
- 切换 Agent / Claude Code 窗口或准备交接；
- 开始长时间运行、真人审核、`resume`、渲染或最终 QC；
- 宣布“当前版本”“最新结果”或准备结束会话。

当前 run 使用 `requirements_checkpoint.json` 保存不可丢失的用户要求，`CURRENT_DELIVERY_FACTS` 保存其路径与 SHA。每次检查点更新后都要同步当前进度、长期记忆和对应 Fxx，并运行：

```bash
python3 main/orchestrator/check_current_delivery_sync.py --check
```

检查不过时，下一位 Agent 必须先修同步，不得依据压缩摘要继续猜。当前音乐硬要求为 `reference-linear-v1`，人声在 `5.000 s` 精确进入；旧 v12 的 `12 s` 入声不得由普通生产入口选择。

## 审核包的特殊规则

审核包的 `ui_sha256` 和 `review_manifest_sha256` 是证据的一部分，不能直接编辑
`review_bundle/index.html`。需要修复页面时：

```text
当前状态必须是 CALIBRATION_REVIEW_REQUIRED
且不能已经有 human_decisions.json 或 review_draft.json
→ refresh-review 归档旧 review_bundle
→ 从同一 calibration_source.json 重建
→ 检查 candidate_id / track / start_sample / end_sample 全部不变
→ 写 review_package_revision.json
```

这样可以恢复审核页的语义上下文、备注、自动保存等能力，同时证明没有偷偷换音频、ASR 或候选。
已有人审决定或草稿时，流程必须停下，不能覆盖审核人的工作。

审核包的可见身份也属于同步事实：`review_package.json` 必须带本次 `run_id` 和由冻结校准选择报告导出的 package-level `review_scope`（高/低风险候选 ID 与计数）。页面必须显示这两个值，并明确候选规则命中置信度**不是**风险级别、更不是自动剪辑授权。同步检查同时校验 package 的范围与 `all_candidates.json`，防止前端把旧候选规则版本、置信度或风险路由误写成“当前版本”。

## ASR 的同步规则

EP04 当前固定沿用外部 `faster-whisper small`（CPU `int8`）及其已验证的词级结果。今后只改
候选、审核页面或渲染参数时，先查 `analysis_reuse_manifest.json`；只有原始输入 SHA、实际送入 ASR
的音频 SHA、模型快照、设备/量化和解码参数全部一致，才允许复用。任何人不得因为新建了 run 就自动重新转写，
也不得把新降噪轨配旧 transcript。

语义分句/标点层只用于审核阅读上下文，必须同时显示“启发式、不能改写原始 ASR/时间戳/删剪决定”的提示。

## 反馈的同步规则

审核人每项可填写一个不超过 500 字的 `feedback` 字段。它必须经过以下链路：

```text
textarea / review_packet
→ localStorage + review_draft.json（草稿，不是人审决定）
→ /api/save：若真实具名审核人已保存 accept/reject，则抽取 human_decisions_and_feedback.live.json（pending 不进入）
→ 新 LABEL-LEARNING-AUTO-* 不可变快照 + 回测 + 原子活动指针（只影响未来新 run）
→ /api/submit（完整审核完成后）
→ human_decisions.json（规范化时不能丢）
→ calibration_report.json / feedback_bundle.json
→ 后续 experience case 的 label.feedback
```

live 标签刷新使用稳定内容 SHA；纯 session/试听时间变化不会重复建快照。若具名审核人将该审核包的全部有效标签撤回为 `pending`，新快照必须显式排除旧 live 标签；只有新快照与回测写完后才可删除旧 live 标签并切换指针，失败时恢复旧文件和旧指针。备注只能解释真人为什么 accept/reject，不能偷偷改变候选边界、决定或自动剪辑政策。

## 当前同步检查入口

```bash
python3 main/orchestrator/check_current_delivery_sync.py --check
```

这个检查会核对当前项目进度中的结构化事实、活动 run 的状态与审核包 SHA、ASR 复用来源、前端必备能力，
以及长期记忆/功能文档是否提到了同一当前 run 和 ASR。检查失败时先修文档或证据，不要绕过检查继续渲染。
