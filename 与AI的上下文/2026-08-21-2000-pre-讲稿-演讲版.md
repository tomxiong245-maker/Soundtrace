二 · 背景 · 为什么这件事有价值
先讲播客本身的 raw material。一期节目一般是 30 到 60 分钟的对话，主持人加两位嘉宾，每个人一支话筒同时录，出来是三条对齐的声音轨。
大家可能觉得后期不就是把'呃'这种口癖剪掉吗？不是。真正的难点有四条。
第一条，一刀一刀剪，而且每一刀都要过渡。
在传统的方法中，音频后期的剪辑需要大量的时间。首先，剪辑者需要把问题一个一个找出来，每一处删除都是一刀，每一刀在波形上都是一个断口。断口如果直接拼上——专业术语叫 butt splice，中文里叫"直拼"——十有八九能听出"很明显的剪辑哼唧（这也是AI 在前期一直存在的典型错误之一）。所以专业剪辑师每一刀都要做一次淡入淡出，用几十毫秒的曲线把断口糊过去，这个手法叫 crossfade，交叉淡化。
一集 60 分钟的深度对话有很多等候选点。理论上就是几十甚至上百次手工过渡。而且过渡长度也不能拍脑袋——如果紧挨着的下一个词是辅音开头，比如"确"这种 q 声母，过渡时间太长会把辅音吃掉，那个词听起来就变成"ue 保"；太短又糊不干净。
这是特别耗神但又不能出错的活。
第二条，音频不应该上云。
在剪辑场景中，未发布的对话内容属于内部数据。所有云端在线工具——像 Descript、Adobe Podcast 这些都需要把数据上传。然而，我们的 Soundtrace 可以在自己电脑上完成。
第三条，语义判断只有人能做。
"这句话是废话还是伏笔？这个停顿是尴尬还是节奏？"如果全用 AI，那么无法得到个性化的结果。我的 mentor 艳馨姐之前就负责音频剪辑，我将她的剪辑成果当做 gold，在“剪哪里”中拥有最高权重，通识，系统也会根据用户的审核结果进行学习。我的目标是让 AI 做他的手，而不是替代他的品味。

四 · 框架 · 从"能力封装"开始
7 个 skill · 按"职责边界"分 6 层
先破题——这些 skill 不是按流程顺序分的 · 是按'边界不能跨'分的。每一层解决一类问题、管一段边界、别的层不许越界改它。

L0 · 门卫层 · episode-triage-and-plan
新一期音频到手先做一件事：判类型比如说3 轨还是 2 轨 · 中文还是双语冻结 plan.json。这一步没做完 · 后面流水线一步都不启动。
这条教训是踩坑踩出来的——早期我写了很多 markdown 文档和规则 · 结果发现 AI agent 干着干着就把规则忘了、乱改乱调。所以现在把关键约束冻结在 plan.json 里 · 每个下游 skill 起动前读 plan · 对不上直接停。规则要冻结在数据里 · 不是文档里。

L1 · "记忆中枢"· feedback-engine
所有反馈进出的唯一入口。每次决策前 agent 必须来这里查历史反馈、每次决策后必须把新反馈存进来。
为什么加它？之前我在 EP04 说"一些"不许剪 · 到 EP05 系统又剪了一次 · 等于每一集都在重新教机器——失忆症。

L2 · 判"剪哪些" · PREFERENCE 层 · 三个 skill
candidate-generation-and-gate（champion）：从原料生成 5 类需要剪辑的问题：（语气词/重复/长停顿/自纠正/串音）
candidate-semantic-veto（challenger）：让 llm 决策
audition-and-delivery（champion · 部分归到 L3）：负责最终的剪辑和审核。

L3 · 判"怎么剪" · PARAMETER 层 · Optuna 独占
这一层的核心是 iterative-cut-refinement-v1（challenger · Stage 6.7）解决怎么剪的问题。

L4 · 学经验 · 跨 episode 沉淀
learning-and-experience（champion · 活的）：
learning-pattern-from-case-v1（challenger · 08-20 骨架 · 未激活）· 用 narrative 语义模式给 LLM 读
L4 硬边界：学习层不能直接改生产链代码。学出来的东西写进 labels_lake / session_feedback / pattern md · 下游 skill 读这些数据源 · 但学习层不能改 gate 阈值、不能改 Optuna 搜索空间、不能改 LLM prompt。

L5 · 治理层 · governance-and-tool-registry
新工具必须先登记 tools.json · 必须有 v2 adapter · 必须声明依赖 SHA · 违反 verify.sh 直接 FAIL。
这条是 M5 元规则的执行者 —— 契约先行、防"偷偷加脚本进生产"。
4.5 六条元规则 · 项目宪法
顶层还有 6 条元规则
M0 · 最高规则 · 开发者模式（覆盖 M1-M6）触发词: 用户输入包含 "开发者模式" 或 "developer mode" (中英不敏感 · 精确匹配)，除了最核心的规则：公司音频不出本地，原始素材只读之外，都可以修改。
值得一提的是，这次在ainol 做实际项目的时候，我发现了做一个项目很多时候需要的是修补思维而不是搭建思维：过多的约束会严重阻碍推进进度。这也是我设立 M0 的原因。
M1 分层 — 生产、实验、每期工作严格隔离
M2 只读 — 原始素材、生产代码、公司音频默认只读，不出机器
M3 人签字 — 语义删剪必须真人明确批准
M4 整数采样点 — 批准的剪辑区间同步作用到三轨上，不容许一个采样点的偏差
M5 契约先行 — 工具必须登记、必须有适配层，未登记即报错
M6 报告纪律 — 说话分三档：已经验证过的事实 / 已经决定的方向 / 还没验证的假设
除了 M0 之外，还有很多元规则也是我踩了不少坑才设立的。等会儿还会有返场。

OK，刚才我讲完了我整个项目能够解决的问题，使用场景，整体的思路和流程。接下来请让我分享我为期一周的踩坑经验。

直到周三下午，同时有 4 个实验组件从实验区晋升到主流水线：pyannote 、NISQA 、Optuna 、案例向量检索一个，全部默认开启。其中后三个是这个项目的重要新能力，我一个一个详细讲。
碰到的第一个问题 · 参数学出来了没人用。 EP04 跑完之后，参数自学习模块学出了一组新参数，保存在一个中间文件里，但没写回到最终生效的剪辑决策清单，渲染阶段用的还是默认值。我听 A/B 对比，很不满意，但是我看到 AI 和我汇报的逻辑没有问题（哈哈，其实后来发现逻辑都有问题），就让 ai 不断地去返工。效果 很差
复盘之后才发现这个问题的本质是"学出来 → 用起来"这条链断了——一堆"接口留着但没有模块接。我后续让 ai 去检查每个小模块和工具的结果是否被消费，才找到了问题，之后加了一个自动回写环节，参数一学出来就强制生效。
第二个问题是· 案例检索只看词，场景全丢。 "呃"这个字在句首、在句中、在紧张停顿之后、在流利叙述当中，是完全不同的场景，但文字上是一模一样的。用文字匹配的话，60 分钟节目里能查到 20 个"呃"，但它不知道哪 20 个真的可比。08-19 加了案例向量检索，用"听起来像"的方式匹配。
之后的几天我依然停滞不前，每次听到 ai 剪的一塌糊涂的版本，找出问题，给 ai 反馈。当时我的想法是用一个 skill 去学习mentor ，youtube 上的高手是怎么剪辑的。这里既包括了剪什么，也包括了怎么剪。但是结果依然很差。

mentor 说，你们要结合具体的案例，不能只讲空话。我真的特别紧张，因为我压根就没有跑通核心的学习流程，甚至连能不能剪干净都无法保证，这让我怎么说。

录制完毕，我回到工位，重新思考我碰到的问题：。这时候我想起上周有幸听过一位同学分享了她在阅读的论文，就是和 skill 相关的。
实在厌倦了和 ai 一轮一轮无产出的交互，我回去重读这篇论文。
它的正文 §4.1 有一句关键的话：
"instead of updating numerical parameters, the Skill is updated along a direction intended to improve expected return..."
翻成人话：作者做 skill 学习的第一件事，是把"数值参数"这一整个维度从 skill 里剔出去——skill 只在语义/模式这一层做梯度上升，数值那一层根本不参与。
还有一句
"Filter out noise and trajectory-specific details, focusing only on recurring patterns."
也就是说，skill 在被更新的每一步，都被强制过滤掉"某一条轨迹上的具体数值"，只留下反复出现的模式。这是方法论层面的硬性设定。
而在附录 F 的 Limitations 里，作者顺手把parameterized procedures列为未来方向——等于亲口承认：现在这套 skill 的自然语言表征，做不了参数化和数值化那一层。
就等于正式宣判我的思路全盘错误。
我想让 ai 学习的是一种模式，这点 skill 确实可以完成。但是具体需要剪辑的时间点，crossfade的值，这根本就不是模式。

想明白了这个问题，我立了一条原则——参数和候选一定要分离。
目前最直接的问题就是剪不干净，也就是参数问题。
我回想起我之前在学校上过的一门课：CSC1006 AI4Science and robotics.里面讲了 神经网络中的参数是用梯度下降训练的。
我便开始寻找有什么可以使用算法，最后就找到了Optuna，这是一个开源的贝叶斯参数优化框架，能够解决参数训练的问题。
那 loss 从哪来？起点就是'以 NISQA discontinuity 作 benchmark'。这是 NISQA 5 维打分里的'不连续性'那一维 · 满分 5.0 · 越高越干净。这就是核心 signal。
有了 signal 就开始推 · 三步：
第一步 · 镜像。Optuna 默认最小化目标 · 我们把 discontinuity 反过来写成 5.0 − discontinuity ·
第二步 · 反作弊。发现问题——如果只用这个 · Optuna 会走捷径 · 通过'根本不剪'拿满分——不剪就没剪口 · discontinuity 自然 5 分。所以加第一个 penalty 让 Optuna 明白'必须真剪掉才算成功'。
第三步 · 挡明显破坏。若基础检查（静音位置）挂了 · 再加 +2.0 惩罚。2.0 比一个漏词轻、比正常 signal 波动重 · 保证 Optuna 不会为了 discontinuity 高一点点就选一个明显有缺陷的参数。
最终 loss 就三项：基础 signal + 反作弊 penalty + 兜底 penalty。
下载完后， 我便扔给 ai 去测试。我也在想如果用算法，那之前在 youtube 上学习的经验，mentor 人工剪辑的样例又有什么意义呢，作为项目最核心的学习能力又应该怎么保留。
实际跑起来的时候，发现10 个案例中有 7 个最终都无法 converge。
我就想到之前打数学建模美赛的时候就碰到过卡在局部最小的问题，突然想到可以让 ai 去把相似情况下 mentor 的参数， youtube 上的经验作为起始点，做一个热启动。最终的结果让我很满意。
之后再候选层也碰到了问题。
参数那边收得差不多了，我心里松一口气，转头把候选也收网。所谓候选，就是"这一段该不该剪"。
早期我是规则派，五族候选加 8 道 gate，觉得很整齐。结果 8-17 用户明确"'一些'不许剪"，下一期系统又剪了一遍。很不幸，ai 患上了失忆症。
我重新回头调研了一下业界的工具，发现这条路线需要大量的数据，而且我自己总结出来的文档离实际产出差距太远，我接了claude code 的 subagent（Claude Haiku4.5），让它直接读原文判 KEEP_CUT / REJECT_KEEP / NEEDS_REVIEW。第一次跑通看到"一些"被标 REJECT_KEEP，我才觉得机器开始有点像人。
接入 llm 其实也是之前就考虑过的方案，但当时ai 给出的路径是接入 api 或者本地部署。特别不 user friendly。更致命的是，我询问了 octo 中的一个 我认为很权威的agent，他也毙掉了这个方案。
08-20 回头看那 8 道 gate，语义的活 LLM 全接管了，我一路砍到 5 道，只负责兜底。合流很简单：只有 LLM 判 KEEP_CUT 才进 EDL，用户签过字的 never_cut 是硬 override，Haiku 也推不翻。EP05 前五分钟 37 个候选、33 自动剪、4 交人审，自动率 89.2%。
之后 我新起一个 learning-pattern-from-case-v1的skill。
它的上游是。
mentor 之前手动剪辑的部分做成的经验卡，
审核人之前审核的candidates 和审核结果。
严格无数字，只出自然语言 pattern，每条模式都挂 case_id 能追溯回原句。

五 · 今后的可延展性
MFA 音素级对齐、剪口检查五项、Optuna 自学习、案例向量检索全部落地之后，基础技术层基本收敛了。后面的迭代重心从"技术攻关"进入"偏好积累"这个阶段。四个方向：
方向一，案例记忆持续积累。 已经有 65 条历史案例，加 33 条人审记录，加 42 条 YouTube 视频学习结果，一共 140 项历史知识在被消费。判决门第 5 关和第 6.8 步向量检索两条通路同时消费。期数越多，记忆越贴合的具体偏好。这套记忆是章鱼 AI 独有的，不是通用模型能给的。
方向二当 learning-pattern-from-case-v2（已经完成）激活之后，会开出把历史案例蒸馏成 LLM 可读的自然语言模式，让主流水线 LLM 那一步的判决直接引用"上一期 mentor 是怎么处理类似情况"的原文证据，而不只是相似度打分。
向量数据库其实很轻。给一段音频 case，用 我们已有的Whisper（语音识别模型）的编码器把它压成一条向量，再用 FAISS（相似度检索库）在历史里找最像的几条。只出相似度分数，不下判决。
具体的框架我已经下载在一个试验区，之所以现在没有投入使用是因为没有足够的案例支撑，所以也没有办法验证证伪。
方向四，Optuna 搜索空间扩展。 现在 Optuna 只对"剪的干不干净“”的候选做参数级迭代。可以优化更多的参数比如说响度阈值、闪避深度、音乐过渡曲线等等。

接下来我要讲几个我的反思。

第一点是需要加入社群，本质上是要让更多信息进入。
本次的ainol项目就让我体会到了社群带来的好处。比如说几位经验丰富的老师，给我讲解论文的金怡同学，每天和讨论到很晚的大神haiyi
都为我提供了很多的思路。这次我能够从坑里走出来我自己觉得有很大的偶然性和戏剧性。我需要更加成体系地保持信息输入。
第二个点就是明确工具的边界
前者需要学习到工具的底层原理。
我个人也因为这次的经验决定今后minor一个cs专业，去更好地认识ai。

第三个点需要运用爱因斯坦的一个思维模式。
科学是从经验到公理，公理到结论，结论反哺经验的过程。
我对我项目的一个感触就是把llm的黑盒不断变成白盒的过程。这其中就是经验到思路（公理）的过程，agent负责的是把思路变成结论。
llm固然能做到拥有很多信息，但是依然有很多不足，比如说跨模式的迁移。
经验到公理的跳跃，也许依然是难以被取代的部分。
