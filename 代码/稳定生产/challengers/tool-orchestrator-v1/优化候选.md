# 优化候选 · tool-orchestrator-v1

> 事实分层：每条标注 `[已验证事实]`、`[已决定的方向]`、`[待验证假设]`；不写“完成、跑通、更准、可发布”等主观词。

## 短期（不动 Champion 即可实现）

- **[已决定的方向]** 给 Champion 注册表的每个 tool 补一个 Challenger adapter，
  使 `main/tools/tools.json` 的 19 项在 runner 下都能通过 `--<param>` 形式调用；
  可以按脚本 argparse 自动生成 shim。
- **[已决定的方向]** 让 runner 支持“跨轨 fan-out”：对 `estimate_sync` 这类
  只接 `track_a / track_b` 的 tool，自动展开为 N×(N-1)/2 次调用，写到子目录。
- **[已决定的方向]** 把 `run_manifest.json` 与 P1 `server_episode.py` 期望的
  bundle 结构对齐，让 runner 直接产出可被 P1 消费的 `tracks.manifest.json`
  + `candidate_source.json`（保留 review-product-v1 的哈希校验）。
- **[待验证假设]** 加一个 `phase=post_review` 的显式 gate：只在读到合法
  `human_decisions.json` 且 reviewer 非自动身份时才允许执行；否则 fail closed。

## 中期

- **[已决定的方向]** 把本 runner 与 Champion `main/orchestrator/orchestrator.py`
  合并；`orchestrator.py` 保留 CREATED / PLANNED / APPROVED / FINALIZED /
  ARCHIVED 顶层状态语义，本 runner 提供 PLAN_FROZEN / RUNNING /
  HUMAN_REVIEW_REQUIRED 的执行段。合并前必须冻结 SHA 与自动测试。
- **[待验证假设]** 用 `main/knowledge/experience_snapshot/` 作为 runner 参考
  知识层入口；能否稳定改进候选质量需要多期数据。

## 长期

- **[已决定的方向]** Loop / MCP 化：把 tool 注册表转成 MCP tool schema，让本
  runner 直接消费 MCP server；`tool_calls.jsonl` 成为审计基础。
- **[待验证假设]** 加入 tool 版本与依赖 SHA 冻结（例：faster-whisper small
  model.bin 的 SHA、ffmpeg 版本）作为计划字段，让 tool 层升级也必须重新冻结
  plan。

## 明确不建议

- 不建议在本 Challenger 里加 approve / finalize / archive；它会与 P1 与
  Champion `orchestrator.py` 语义冲突。
- 不建议提前让 runner 调用 `render_approved_edl` 或 `assemble_program`；应在
  Champion 层完成人工审核后再跑，且这些属于 post_review。
- 不建议把 `main/tools/tools.json` 与 Challenger `registries/adapters.tools.json`
  合并；两者是不同职责（Champion 声明 vs. Challenger 桥接），合并会破坏
  “Champion 不变”边界。
